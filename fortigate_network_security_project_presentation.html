Slide 02 / Foundations

Project Scope & Core Engineering Requirements

Designed to simulate an enterprise boundary connecting a remote Branch location to Corporate Headquarters through dual non-cooperating ISPs, enforcing zero-trust access and unified security profiling.

1. Administrative RBAC

Dedicated tiering with Super Administrator (super_admin) and custom Read-Only compliance auditor profiles.

2. Interface Isolation

Dedicated Out-of-Band management plane (port1) isolated from transit traffic on dual WANs and LANs.

3. Layer-8 Identity Auth

Local directory groups enforcing active user credential validation before permitting inter-site routing.

4. Flow-Based UTM Profiles

Real-time signature inspection across Antivirus (stream-based) and IPS sensor detection engines.

5. Dual Route-Based IPsec

Two independent Phase 1 / Phase 2 tunnels establishing routable point-to-point overlay interfaces.

6. SD-WAN & Path Probing

Active-standby member bundling with automated health SLA probes monitoring peer gateway reachability.

Architectural Note: High Availability (HA) was deliberately excluded to honor the hypervisor memory ceiling of two FortiGate VM nodes. 2x VMs Active

Slide 07 / Overlay Architecture

Dual Route-Based IPsec VPN Design

Active-Standby Tunnels

To support non-disruptive failover, two independent route-based virtual tunnel interfaces were established over the physical WAN underlays.

Primary Tunnel: WAN 1 PRIORITY 10

Binds directly to physical underlay port3.

Tunnel Name: HQ-BRANCH-WAN1
Underlay Peering: 198.51.100.1 ↔ 198.51.100.2
Phase 2 Selectors: 10.10.10.0/24 ↔ 10.20.20.0/24
Backup Tunnel: WAN 2 FLOATING DISTANCE 20

Binds directly to secondary physical underlay port4.

Tunnel Name: HQ-BRANCH-WAN2
Underlay Peering: 198.51.200.1 ↔ 198.51.200.2
Phase 2 Selectors: 10.10.10.0/24 ↔ 10.20.20.0/24
Route-Based Tunnel Advantages: Route-based VPNs present virtual interfaces (tun_id) to the kernel, allowing standard static routes, dynamic routing protocols (BGP/OSPF), and SD-WAN health metrics to steer traffic dynamically without re-writing Phase 2 access lists.
Slide 08 / Forensic Finding

Cryptographic Reality & Virtual Licensing

CLI Error -61 Investigation
Observed Failure (HQ & Branch CLI) 
FGT-HQ (phase1-interface) # edit "To_Branch_VPN"
FGT-HQ (To_Branch_VPN) # set proposal aes256-sha256
command parse error before 'aes256-sha256'
Command fail. Return code -61
Academic Transparency Mandate: Standard presentations falsely claim AES-256/SHA-256 was implemented. In our lab, the production running configuration actually negotiated and stabilized under des-sha256 / des-md5.

Root Cause Engineering Breakdown

The virtual appliance runs on Fortinet's evaluation VM disk image. Under US export compliance and free trial licensing restrictions:

  • High-grade hardware crypto acceleration is locked without a registered FortiCare trial or production license.
  • The CLI parser strips 256-bit AES algorithms from the valid proposal grammar.
  • Auto-discovery via set proposal ? confirmed allowed ciphers: des-md5, des-sha1, des-sha256.
Negotiated Suite: Phase 1 & 2 = DES-SHA256 / DH Group 5 & 14

Slide 10 / Policy Engineering

Policy Consolidation & VM Table Limits

CLI Error -23 Workaround
Encountered Hardware Ceiling

When configuring granular per-tunnel bidirectional firewall policies (Policy 21, Policy 100), FortiOS halted:

reached the maximum number of entries
Command fail. Return code -23

Unlicensed FortiGate VMs enforce strict policy table constraints to limit hypervisor RAM allocations.

Architectural Consolidation (Policy 10) 
config firewall policy
    edit 10
        set name "LAN_to_IPsec_Outbound"
        set srcintf "port2"
        set dstintf "HQ-BRANCH-WAN1" "HQ-BRANCH-WAN2"
        set srcaddr "HQ_LAN"
        set dstaddr "BRANCH_LAN"
        set action accept
        set schedule "always"
        set service "ALL"
        set logtraffic all
    next
end
Bundling both tunnel interfaces into a single policy resolved table exhaustion without sacrificing inspection posture.

Slide 15 / Root Cause Analysis

Data-Plane Encapsulation Investigation

Definitive Diagnostic Finding
The Critical Metric Anomaly: Zero Packet Processing
proxyid=To_HQ_P2 proto=0 sa=1 ref=2 serial=2
dec:pkts/bytes=0/0, enc:pkts/bytes=0/0 ← ENCRYPTION RING BYPASS
1. Virtual NPU Offload Desync: In KVM evaluation images, FortiOS defaults to assigning crypto work to virtual acceleration rings (npu_flag=00). When cryptographic suites were swapped on-the-fly from AES to DES, the kernel session table desynchronized from the software IPsec driver.
2. SD-WAN Zone Interface Ownership: Physical interfaces were locked inside the default SD-WAN zone (virtual-wan-link). Modifications produced operator error -23, establishing an internal kernel ownership contention between the SD-WAN physical underlay and route-based IPsec overlays.
Academic Significance: Demonstrating rigorous methodology by isolating a control plane success (sa=1) from a data plane drop proves deep network engineering fluency far beyond simple ping pass/fail scenarios.
Slide 16 / Roadmap & Appendix

Remediation Roadmap & Diagnostic Toolkit

Project Conclusion
Essential Diagnostic Commands
  • diagnose vpn ike gateway list (Phase 1)
  • diagnose vpn tunnel list (Phase 2 & Enc/Dec)
  • get router info routing-table all (FIB)
  • diagnose firewall iprope lookup ... (Policy ID)
  • diagnose debug flow trace start 10 (Kernel)
  • diagnose sniffer packet port3 'proto 50' (ESP)
Production Remediation Blueprint
  1. Clean Cold Boot: Initialize nodes with DES proposals pre-compiled prior to initial interface bindings to eliminate dynamic SA key desyncs.
  2. Overlay SD-WAN Bundling: Group the virtual IPsec interfaces directly into the SD-WAN zone rather than the physical underlay ports.
  3. Licensing: Link nodes to a free FortiCloud evaluation token to enable AES-256 and hardware offload engines.
  4. High Availability: Deploy active-passive FGCP clustering once compute resources permit additional VM allocations.
